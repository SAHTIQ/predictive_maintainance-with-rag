# Database Design

## Database Choice and Conventions

The system uses PostgreSQL. The initial schema contains only the six required tables: `users`, `machines`, `sensors`, `sensor_readings`, `maintenance_events`, and `predictions`.

- Every table has a primary key named `id`.
- IDs are generated by the database or application according to one consistent implementation choice; the exact ID type is **To be decided during implementation**.
- All timestamps are stored in UTC using PostgreSQL timezone-aware timestamps (`timestamptz`) unless the implementation documents an equivalent convention.
- `created_at` and `updated_at` are system-managed timestamps. `updated_at` changes when a mutable record changes.
- Source sensor values are not silently overwritten during cleaning. Quality problems are represented by `data_quality_status`.
- All foreign keys reference existing records. Delete behavior must protect historical readings and predictions; exact `ON DELETE` behavior is **To be decided during implementation**.

## Tables

### users

Purpose: stores authenticated users and their roles.

Important columns:

- `id`: primary key.
- `name`: required display name.
- `email`: required login identifier; unique and normalized for comparison.
- `password_hash`: required password hash; plaintext passwords are never stored.
- `role`: required role such as viewer, maintenance user, or administrator.
- `created_at`, `updated_at`: UTC audit timestamps.

Constraints: unique email, required name/email/password hash/role, and a role value restricted to supported roles.

### machines

Purpose: stores equipment metadata.

Important columns:

- `id`: primary key.
- `machine_code`: required machine identifier; unique.
- `name`: required human-readable name.
- `machine_type`: required or explicitly nullable according to implementation validation.
- `location`: installation location.
- `status`: operational status such as active, inactive, or maintenance.
- `created_at`, `updated_at`: UTC timestamps.

Constraints: unique `machine_code`, valid status values, and required identifying fields.

### sensors

Purpose: defines sensors installed on machines.

Important columns:

- `id`: primary key.
- `machine_id`: required foreign key to `machines.id`.
- `sensor_code`: required code unique within a machine.
- `sensor_type`: vibration or temperature for the initial scope.
- `unit`: normalized measurement unit.
- `sampling_rate`: configured sampling rate, with a positive-value constraint when present.
- `created_at`: UTC creation timestamp.

Constraints: unique (`machine_id`, `sensor_code`), supported sensor type, valid unit for sensor type, and positive sampling rate when supplied.

### sensor_readings

Purpose: stores timestamped source measurements used for analysis.

Important columns:

- `id`: primary key.
- `machine_id`: required foreign key to `machines.id`.
- `sensor_id`: required foreign key to `sensors.id`.
- `timestamp`: UTC time at which the measurement occurred.
- `measurement_type`: vibration or temperature.
- `value`: numeric measurement value.
- `unit`: unit supplied or normalized for the measurement.
- `source`: origin such as import, sensor, or sample data.
- `data_quality_status`: valid, missing, duplicate, invalid, out_of_range, or another documented status.
- `created_at`: UTC ingestion timestamp.

Constraints: machine and sensor must be associated, required numeric and timestamp fields must be present, and measurement type/unit must be compatible. A duplicate definition for the same source, sensor, and timestamp is **To be decided during implementation**; duplicate records must still be detectable and reported.

### maintenance_events

Purpose: stores historical and recorded maintenance activity for context and review.

Important columns:

- `id`: primary key.
- `machine_id`: required foreign key to `machines.id`.
- `event_type`: required event category.
- `timestamp`: UTC event time.
- `description`: event details when available.
- `created_at`: UTC record creation time.

Constraints: machine and event type are required. Event types and maximum description length are **To be decided during implementation**.

### predictions

Purpose: stores versioned analysis results associated with a machine and prediction time.

Important columns:

- `id`: primary key.
- `machine_id`: required foreign key to `machines.id`.
- `timestamp`: UTC time represented by the result.
- `health_score`: calculated health value with a documented scale.
- `health_state`: normal, warning, critical, or another documented state.
- `anomaly_score`: model output.
- `anomaly_severity`: readable severity.
- `rul_value`, `rul_unit`: RUL estimate and unit when available.
- `risk_level`, `risk_score`: maintenance risk result.
- `maintenance_priority`: recommended priority.
- `maintenance_window`: recommended review or maintenance window.
- `model_version`: model/configuration identifier.
- `created_at`: UTC result creation time.

Nullable RUL fields are permitted when data is insufficient. Missing-result behavior for other fields is **To be decided during implementation**, but partial results must be clearly labeled rather than treated as reliable.

## Relationships

```text
users       has authenticated access to application resources
machines    1 ---- many sensors
machines    1 ---- many sensor_readings
sensors     1 ---- many sensor_readings
machines    1 ---- many maintenance_events
machines    1 ---- many predictions
```

A sensor reading references both its machine and sensor so that queries can be filtered efficiently and the relationship can be validated. The backend must reject a reading where `sensor_id` belongs to a different `machine_id`.

## Indexing and Query Considerations

The initial implementation should index foreign keys and common time-series access paths, especially readings by (`machine_id`, `timestamp`), predictions by (`machine_id`, `timestamp`), and maintenance events by (`machine_id`, `timestamp`). Exact index definitions are **To be decided during implementation** after query tests. No additional tables are required for the pilot.

## Security and Integrity

- Password hashes are stored instead of passwords.
- Role values and access checks are enforced by the backend.
- Foreign keys prevent orphaned domain records.
- Validation rejects malformed timestamps, unsupported units, and invalid numeric values.
- Database credentials and secrets are supplied through deployment configuration, not source files.
