# Stage 10 — Database Architecture & Telemetry Persistence

This document details the persistence architecture for the Predictive Maintenance Vibration Monitoring System with Context-Aware RAG.

---

## 1. Architectural Overview

The persistence layer integrates the core telemetry ingestion with Stages 6 through 9:

```
+-------------------------------------------------------------------------------+
|                       Sensor Telemetry Ingestion                              |
|          (Dataset V3: 50 machines, 10,000 baseline observations)             |
+-------------------------------------------------------------------------------+
                                      |
                                      v
+-------------------------------------------------------------------------------+
|                         SQLAlchemy ORM Data Store                             |
|       (PostgreSQL in Production / SQLite with StaticPool in Dev & Tests)      |
|                                                                               |
|   - machines (Core machine registries & configuration)                        |
|   - sensor_readings (Chronological 30-min vibration & temp telemetry)         |
|   - health_records (Stage 6: Adaptive Health Engine evaluations)              |
|   - risk_records (Stage 7: Maintenance Risk Engine scores & windows)          |
|   - maintenance_records (Technician logs & historical service events)         |
|   - recommendation_records (Stage 9: Grounded 4-tier recommendation decisions)|
+-------------------------------------------------------------------------------+
                                      |
                                      v
+-------------------------------------------------------------------------------+
|                        FastAPI Database Endpoints                             |
|                                                                               |
|   - GET /api/v1/machines                                                      |
|   - GET /api/v1/machines/{id}                                                 |
|   - GET /api/v1/machines/{id}/sensor-history                                  |
|   - GET /api/v1/machines/{id}/health-history                                  |
|   - GET /api/v1/machines/{id}/risk-history                                    |
|   - GET /api/v1/machines/{id}/maintenance-history                             |
|   - GET /api/v1/machines/{id}/latest                                          |
|   - GET /api/v1/fleet/overview                                                |
+-------------------------------------------------------------------------------+
```

## 2. Table Specifications & Indexes

### 2.1 `machines`
Primary registry of monitored assets.
* `id` (INTEGER, PK)
* `machine_id` (VARCHAR(50), UNIQUE, NOT NULL, INDEX)
* `machine_type` (VARCHAR(50), NOT NULL)
* `machine_name` (VARCHAR(100), NULLABLE)
* `installation_date` (TIMESTAMP WITH TIME ZONE, NULLABLE)
* `status` (VARCHAR(20), DEFAULT 'active')
* `created_at`, `updated_at` (TIMESTAMP WITH TIME ZONE)

### 2.2 `sensor_readings`
High-resolution 30-minute sampled vibration and operational telemetry.
* `id` (INTEGER, PK)
* `machine_id` (VARCHAR(50), FK -> `machines.machine_id`, INDEX)
* `timestamp` (TIMESTAMP WITH TIME ZONE, NOT NULL, INDEX)
* `temperature` (FLOAT, NOT NULL)
* `vibration_x`, `vibration_y`, `vibration_z` (FLOAT, NOT NULL)
* `vibration_magnitude` (FLOAT, NOT NULL)
* `load_percent`, `rotational_speed` (FLOAT, NULLABLE)
* `operating_hours` (FLOAT, NOT NULL)
* `created_at` (TIMESTAMP WITH TIME ZONE)
* **Composite Index**: `idx_sensor_machine_ts (machine_id, timestamp)` for $O(\log N)$ historical range scans.

### 2.3 `health_records`
Chronological health evaluation snapshots generated by Stage 6.
* `id` (INTEGER, PK)
* `machine_id` (VARCHAR(50), FK -> `machines.machine_id`, INDEX)
* `timestamp` (TIMESTAMP WITH TIME ZONE, NOT NULL)
* `health_score` (FLOAT, NOT NULL, 0–100)
* `health_state` (INTEGER, NOT NULL: 0=Good, 1=Warning, 2=Critical)
* `health_state_label` (VARCHAR(20), NOT NULL)
* `anomaly_status` (BOOLEAN, NOT NULL)
* `anomaly_score` (FLOAT, NULLABLE)
* `degradation_status` (VARCHAR(50), NOT NULL)
* `degradation_rate` (FLOAT, NULLABLE)
* `rul_hours` (FLOAT, NULLABLE)
* **Composite Index**: `idx_health_machine_ts (machine_id, timestamp)`

### 2.4 `risk_records`
Operational risk scores and prioritized maintenance windows generated by Stage 7.
* `id` (INTEGER, PK)
* `machine_id` (VARCHAR(50), FK -> `machines.machine_id`, INDEX)
* `timestamp` (TIMESTAMP WITH TIME ZONE, NOT NULL)
* `risk_score` (FLOAT, NOT NULL, 0–100)
* `risk_level` (VARCHAR(20), NOT NULL: LOW, MEDIUM, HIGH, CRITICAL)
* `maintenance_priority` (VARCHAR(50), NOT NULL: P0, P1, P2, P3)
* `maintenance_window` (VARCHAR(100), NOT NULL)
* `risk_factors` (JSON, NULLABLE)
* **Composite Index**: `idx_risk_machine_ts (machine_id, timestamp)`

### 2.5 `maintenance_records`
SOP-compliant repair logs and preventative maintenance activities.
* `id` (INTEGER, PK)
* `machine_id` (VARCHAR(50), FK -> `machines.machine_id`, INDEX)
* `maintenance_date` (TIMESTAMP WITH TIME ZONE, NOT NULL, INDEX)
* `maintenance_type` (VARCHAR(50), NOT NULL)
* `component` (VARCHAR(50), NOT NULL)
* `description` (TEXT, NOT NULL)
* `action_taken` (TEXT, NOT NULL)
* `sop_code` (VARCHAR(50), NULLABLE)
* `technician_notes` (TEXT, NULLABLE)

### 2.6 `recommendation_records`
Fully grounded, 4-tier explainable decisions generated by Stage 9.
* `id` (INTEGER, PK)
* `machine_id` (VARCHAR(50), FK -> `machines.machine_id`, INDEX)
* `timestamp` (TIMESTAMP WITH TIME ZONE, NOT NULL)
* `condition_summary` (JSON, NOT NULL)
* `health_score` (FLOAT, NOT NULL)
* `health_state` (VARCHAR(20), NOT NULL)
* `rul_hours` (FLOAT, NULLABLE)
* `risk_score` (FLOAT, NOT NULL)
* `risk_level` (VARCHAR(20), NOT NULL)
* `maintenance_priority` (VARCHAR(50), NOT NULL)
* `maintenance_window` (VARCHAR(100), NOT NULL)
* `potential_causes` (JSON, NOT NULL)
* `recommended_actions` (JSON, NOT NULL)
* `reasoning` (TEXT, NOT NULL)
* `confidence` (FLOAT, NOT NULL)
* `measured_evidence` (JSON, NOT NULL)
* `calculated_evidence` (JSON, NOT NULL)
* `retrieved_documentary_evidence` (JSON, NOT NULL)
* `source_traceability` (JSON, NOT NULL)
* **Composite Index**: `idx_rec_machine_ts (machine_id, timestamp)`

## 3. Ingestion & Temporal Leakage Prevention

1. **Strict Idempotency**:
   `scripts/ingest_dataset_v3.py` checks existing `(machine_id, timestamp)` pairs. Re-running the script inserts 0 duplicates.
2. **Chronological Machine Telemetry**:
   `DatabasePipelineService.load_machine_dataframe` queries historical sensor data ordered by `timestamp.asc()`.
3. **Rolling Window Integrity**:
   Requires $k \ge 5$ sequential observations strictly prior to or including the evaluation timestamp, guaranteeing that no future telemetry leaks into feature calculations or risk assessments.
